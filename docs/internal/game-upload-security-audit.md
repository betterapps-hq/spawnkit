# Game upload and browser isolation security audit

Reviewed 16 October 2026; production acceptance pass repeated 17 October 2026. Scope: source uploads, remote builds, media processing, artifact delivery, homepage media, embedded players, authentication and resource abuse. This is a code and configuration review with targeted browser tests, not a penetration-test certification.

Game hosting uses the separate `spawnkit.games` registrable domain. Listing media now runs in a fresh sandbox after the creator build has been destroyed, and build traffic is restricted at the provider boundary. Storage reservations/retention and worst-case upload load validation remain open. CSP reduces exposure; it does not replace process isolation. See the 17 October follow-up below and the [API authorization audit](api-authorization-audit.md).

## Findings and priorities

No creator code or scripts are added. ### Cookie finding limitations

The original synthetic browser test demonstrated parent-cookie injection from the old game domain, not theft of a user's real session. The updated test uses `.games` and confirms both reading and overwriting `.cloud` cookies fail. A separate live signed-in audit recorded names and attributes only: `__session` and its suffixed variant are host-only on `spawnkit.cloud`, Secure and SameSite=Lax; `__client` is HttpOnly and scoped to `.clerk.spawnkit.cloud`. Clerk's `__client_uat` timestamp cookies remain parent-scoped on `.spawnkit.cloud`. No cookies were applicable to game hosts. The temporary audit session was revoked immediately afterward; no cookie values, sign-in tokens or browser storage state were saved. Session cookies are intentionally JavaScript-readable for Clerk's client SDK; changing that independently would break authentication. See [Clerk's authentication architecture](https://clerk.com/docs/guides/how-clerk-works/overview) and [cookie domain rules](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie).

The new game domain must never receive platform session cookies. Provisioning updates exact telemetry origins alongside current environment and deployment addresses; the application CSP permits game frames and media only on `.games`.

### Artifact transfer correction and hardening

The earlier review overstated the manifest buffering risk: the pinned Sandbox SDK's `readFile(path, {encoding: "none"})` returns a raw `ReadableStream`, not an already-buffered string. `readArtifactManifest` now checks the advertised file size before consuming bytes and cancels immediately above 30 MiB. It independently counts streamed bytes and cancels overflow even if the build changes the file or the advertised size is inaccurate. JSON parsing only begins after that bound passes. Unit tests cover invalid sizes without pulling the stream, the exact limit, and an undersized claim followed by oversized content. General near-limit allocation/concurrency load validation remains open.

### Media finding limitations

The control Worker independently checks output paths, canonical base64, 2,000 files and a 20 MiB artifact total. Catalog media is checked again in R2: covers must be small bounded WebP containers and trailers bounded H.264 MP4 containers, with matching content-derived filenames. Those checks prevent a 100 MiB homepage image and reject arbitrary HTML/SVG as processed cover art.

However, a content hash proves byte identity, not that the trusted encoder produced those bytes. Header/container inspection is not complete pixel or video-bitstream decoding. An attacker who controls the build sandbox can forge a plausible processed artifact. The current design should be described as bounded output validation, not tamper-proof platform transcoding. No cross-job container escape was demonstrated. Cloudflare explicitly treats the entire sandbox as one trust unit, including processes, files and localhost ports; a different Unix user is insufficient. See [Cloudflare Sandbox security](https://developers.cloudflare.com/sandbox/concepts/security/).

The fresh media job should receive only the selected files and bounded manifest, never the source project or its package scripts. Run decoders with no outbound network, fixed resources/timeouts, no shared writable state with build jobs, and return a platform-owned output manifest. Keep the current Worker byte/format checks as an additional layer.

## CSP design

### Application policy

The dashboard Worker entrypoint generates a fresh cryptographic nonce per request, overwrites any incoming nonce header and supplies the value to the router, theme script, streamed hydration and Clerk. HTML is `private, no-store` so a nonce-bearing document is not shared through a cache. Client navigation continues under the initial document's policy and nonce; it does not weaken policy when a route changes.

The app allows its own executable files, the exact Clerk frontend host derived from the configured publishable key, Clerk protection endpoints, Cloudflare challenges, and the platform's Cloudflare analytics script. It permits game hosts for frames and artwork/video, **not** executable scripts or API connections. The game-host wildcard is a discovery/embedding capability, not a claim that all subdomains are trusted. Database-produced URLs still determine what is embedded. `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`, and `script-src-attr 'none'` restrict plugins, URL-base injection, clickjacking and inline event handlers. JavaScript `unsafe-eval` and script `unsafe-inline` are absent; `wasm-unsafe-eval` allows WebAssembly used by the app's game demos. Inline styles remain allowed for Clerk and existing component styling.

The configuration is an HTTP `Content-Security-Policy` response header. The browser enforces it on the client; React does not need to reimplement CSP. A meta-only policy would not support all relevant directives, including `frame-ancestors` and `sandbox`. Neither an iframe `allow` attribute nor the parent's CSP alone constrains all code inside a separately loaded game document. See [CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy) and [Clerk CSP requirements](https://clerk.com/docs/guides/secure/best-practices/csp-headers).

Only `/cli/authorize` permits form submission to the exact configured Clerk origin and the fixed `http://127.0.0.1:43819/callback` destination. Chromium checks form redirects as well as the original action, so the loopback callback must be explicitly permitted. Other application pages retain `form-action 'self'`. CLI routes also load Clerk's consent UI; the public site's deferred UI setting cannot be used on the consent page. See [form-action redirect behavior](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/form-action).

### Game policy

Every game artifact response receives the policy, including cache hits, byte ranges, conditional responses and HEAD. This prevents stale cached headers or a range response from bypassing protection. Platform host forwarding remains outside the game policy.

The policy uses `sandbox allow-scripts allow-same-origin`, permits same-origin game resources, denies nested frames, plugins and form submission, and limits embedding to explicit platform origins. Scripts remain allowed inline inside the untrusted game because uploaded games contain arbitrary executable code by design. JavaScript evaluation is also permitted inside games for existing Pixi shader/uniform helpers; the account site does not grant that exception. WebAssembly and blob workers are supported. Network connections are limited to the game itself and named platform telemetry/analytics services. Google Fonts styles and fonts are explicit compatibility exceptions for existing games. Camera, microphone, location, payment, USB, serial, Bluetooth, clipboard and display capture are disabled by Permissions-Policy. Fullscreen/gamepad remain available through the player.

This is a policy for the current hosted static games. Arbitrary CDNs, ad scripts, third-party APIs, external multiplayer endpoints and Sentry endpoints are not automatically allowed. Future requirements need a validated capability contract and compatibility testing; an uploaded config must not be able to relax the app's CSP. A CSP cannot remove malicious gameplay, deceptive content, arbitrary computation, all navigation, or browser-engine vulnerabilities. It also does not stop a game from accessing storage/cookies already available to its own origin.

## Verification and rollout

Initial live inspection confirmed missing CSP/Permissions-Policy on the app and game HTML. R2 inspection confirmed private storage. The package audit identified the Sharp advisory; dependency and Docker pins were updated. See [the upstream advisory](https://github.com/advisories/GHSA-wq5f-xc86-pv6w) for the affected SVG decoder and runtime conditions.

`tests/security-policy.spec.ts` uses intercepted fixed-domain pages in fresh browser contexts to check unauthorized inline and game-host scripts, game-to-parent DOM access, outbound fetch, JavaScript eval, popup/top navigation, and cross-site cookie separation. The tests also verify the intentional game-only evaluation exception. These tests do not use real account cookies or send attack traffic to production. Desktop and mobile Chromium checks pass.

`tests/app-csp.spec.ts` checks deployed response headers, nonce changes, hydration, client navigation and sign-in UI. It is opt-in with `SPAWN_LIVE_CSP=1`. `tests/hosted-game-security.spec.ts` loads all published games in a fresh browser and checks their actual response policies and runtime errors; `SPAWN_CANDIDATE_CSP=1` substitutes candidate headers before a rollout. Both checks passed against production on desktop and mobile. A separate synthetic consent form test verifies the Clerk-to-loopback redirect with a local test callback server; it runs on desktop only to avoid competing for the fixed callback port. Cached HTML, HEAD, 304 and 206 responses also retained the live game policy. These are targeted checks, not proof of safety for every future game or every browser. Firefox/Safari-specific verification, worst-case upload load tests, decoder fuzzing, container OS vulnerability scanning and adversarial sandbox egress testing remain separate work.

The rebuilt image is `sha256:27648faf57a210f0ca4943e68193ec8dd0a5818b0f69f1dee7954913eca545c1`. Staging application version 14 and production version 6 use it, with all three instances healthy in each environment. Running the exact image with networking disabled reported Sharp 0.35.5. The final package audit found zero known advisories; this is not a container OS scan or a guarantee of no unknown vulnerabilities. `pnpm verify` and standalone generated-project smoke checks for Pixi, Phaser, Babylon and Three passed.

Keep the player loading/retry redesign in Storybook until approved. A native iframe `load` event is not evidence of successful game startup: browsers deliberately hide some iframe load failures. Production readiness UI needs an origin-and-source-checked game handshake, a timeout and an honest retry path.

## Recommended order

1. Completed: separate game hosting from the account site's registrable domain and verify host-only session cookies.
2. Completed: independent trusted media jobs with final byte validation.
3. Administrative quarantine is implemented; upload/storage reservations and retention cleanup remain.
4. Build network controls are deployed and staging-tested. Continue worst-case upload/concurrency and malformed-media validation.

Do not expand open uploads based solely on CSP passing. Storage admission/retention and upload memory/load validation remain the next architectural work. Manage, Reports and Team are connected to production records with server-side Admin/Moderator/Observer permissions, transactional audit history, immutable evidence and enforced hosting restrictions. Storybook continues to use isolated example records.

## Isolation and authorization follow-up — 17 October 2026

The media job now has a distinct `media-<deployment>` sandbox identity, separate from `build-<deployment>`. The Worker validates the raw artifact manifest, destroys the creator sandbox, and copies only selected media (cover at most 1 MiB, trailer at most 2 MiB) plus bounded metadata into the fresh processor. Only the platform's Sharp/FFmpeg runner executes there. Final media paths must match content hashes and pass byte/format checks. Creator-generated files in the reserved processed-media namespace are discarded before trusted results are merged. Failure cleanup destroys both sandboxes before releasing the shared build reservation; a surge queues behind the existing three-job capacity.

The same pinned SDK remains in use. The application overrides `enableInternet=false`, enables HTTPS interception, and switches provider-owned outbound handlers between installation and build. Installation permits only GET/HEAD to `https://registry.npmjs.org` with no redirects, credentials, custom request headers or query strings. Package lifecycle scripts and pnpmfile hooks are disabled. The build and media phases deny HTTP(S). Creator processes cannot restore the provider's outbound policy from inside the container. Cloudflare DNS resolution remains available, so this is not a DNS-exfiltration boundary; secrets are not supplied to the build. Private registries, git URL dependencies and build-time external downloads are not supported by this policy.

An isolated staging fixture installed `is-number@7.0.0` from the registry, then verified 403 responses for app HTTPS, app HTTP and registry HTTPS during the build. A request to port 8443 failed. The unprivileged build could not overwrite the processor file. It submitted a forged processed-media filename; the Worker removed it. The fresh media container generated a 498-byte WebP and 12,024-byte MP4, whose hashes, types, sizes and stored listing references were checked in R2. Both sandboxes used image `sha256:a8ff181c90c3def338d21b69f19c142c663ebdd5688460036b9a5e25171bb927` and were inactive afterward. The fixture deliberately had no supported hosting environment: artifacts became ready, activation stopped, and no game was published. Its temporary records and R2 objects were removed after verification.

The review authorization race and audit mutability were fixed as described in [API and record authorization](api-authorization-audit.md). Migration 0021 was applied in staging and production. Existing review decisions remain intact and appear in Manage history; new events retain actor/title snapshots. D1 authorization is enforced by application queries and transaction guards, not native row-level security.

Validation: `pnpm verify` passed, including 229 control-API tests. Production HTTP acceptance repeated all 32 checks successfully. Desktop/mobile browser acceptance passed for the ranking layout, publishing interactions, app nonces, game CSP, framing and cookie boundaries. One stale browser test still expected the retired `.cloud` game domain; its interception/assertion were updated to `.games` and both device runs passed. Three inapplicable mobile/hover cases were skipped. See ignored `work/security-*` logs for the exact runs.

Deployed Worker versions: staging control `4f4111e2-0c85-4c07-be7e-6fb22e800603`, production control `bc32b8cd-609b-4192-b5aa-26fd686f8d07`, production dashboard `982f4aa6-27ea-4ff7-80dd-8ac746ed0063`. Production container version 7 selects the tested image at 100 percent; old inactive container records can still refer to the previous image.

This changes new builds. Existing releases are immutable and have not been mass-reprocessed. Storage quotas/retention, concurrent near-limit archive tests, decoder fuzzing, OS image scanning and Firefox/Safari verification remain outside this completed pass.
